Lab M6.03 - Build Dashboard for Web Tier Health

Repository: https://github.com/cloud-engineering-bootcamp/ce-lab-build-dashboard-web-tier

Activity Type: Individual
Estimated Time: 45 minutes

Prerequisites

  • Amazon Linux 2023 EC2 instance tagged Name=logging-lab from Lab M6.01, with the application and CloudWatch agent running
  • CWAgent metrics collection enabled per Lab M6.02 Part 3 (mem_used_percent, disk_used_percent); without it the Memory and Disk widgets below show no data
  • AWS CLI configured with permissions for CloudWatch
  • A load balancer is optional and not something either prior lab creates. Widgets that use AWS/ApplicationELB metrics (Request Rate, Error Rate, Latency, Target Health) only work if you have one; remove or ignore them otherwise

Learning Objectives

  • Design effective dashboard layout
  • Create CloudWatch dashboard with multiple widgets
  • Display key metrics (Request Rate, Error Rate, Latency)
  • Use appropriate visualizations
  • Implement correlation views

Your Task

Build a comprehensive monitoring dashboard for your web tier (Load Balancer + EC2 instances) that provides at-a-glance health status.

Success Criteria:

  • Dashboard shows Golden Signals (Latency, Traffic, Errors, Saturation)
  • Multiple widget types used appropriately
  • Clear visual hierarchy
  • Dashboard is actionable

Otherwise, this stands up a minimal ALB and target group pointed at your Lab M6.01 instance, so those widgets show real data instead of "--". Run at least the INSTANCE_ID lookup at the top regardless, the CPU, Memory, Network, and Disk widgets need it and have nothing to do with the load balancer. LB_DIMENSION, TG_DIMENSION, and INSTANCE_ID all feed directly into Part 3.

Before running any of this, confirm the app is actually up: SSH in and run curl http://localhost:5000/health. Lab M6.01 Part 4 started it in the foreground of an SSH session, so if that session has since closed, which by the time you reach this lab is likely, the app is down. A dead app is by far the most common reason the target below never goes healthy, regardless of how correctly the load balancer and security groups are configured. Restart it persistently, so it survives you disconnecting again:

on the instance directly, like Part 4 of Lab M6.01 does, never touches the ALB. Get the ALB's DNS name and generate traffic against that instead:

Key Metrics to Include:

  • Request rate (requests/minute)
  • Error rate (% and count)
  • Latency (P50, P95, P99)
  • Target health (healthy target count)
  • CPU utilization
  • Memory utilization
  • Network throughput
  • Disk usage

Part 2: Create Dashboard JSON (15 min)

Every widget below hardcodes region as us-east-1. Replace that with whatever region your instance and log group actually live in, or the dashboard will load with no data even though everything else is correct.

Every AWS/ApplicationELB, AWS/EC2, and CWAgent metric below also needs explicit dimensions, without them CloudWatch has no way to know which load balancer or instance to read, and the widget just shows "No data available" or "--". YOUR_LB_DIMENSION, YOUR_TARGETGROUP_DIMENSION, and YOUR_INSTANCE_ID are placeholders throughout; they get substituted in Part 3 with sed, using the $LB_DIMENSION, $TG_DIMENSION, and $INSTANCE_ID values from the Optional Setup section above (INSTANCE_ID is captured there regardless of whether you set up a load balancer). If you already have your own load balancer instead, derive the first two from it:

HealthyHostCount and UnHealthyHostCount need both LB dimensions; the other ALB metrics only need LoadBalancer. Every AWS/EC2 and CWAgent metric (CPU, Memory, Network, Disk) needs InstanceId.

Widget Object Keys: every entry in the widgets array, text or metric, shares the same outer shape, then branches by type:

  • type: "text" or "metric"
  • x, y: position in a 24 column grid, y grows downward
  • width, height: size in grid units
  • properties: everything else about the widget, its contents depend on type

For text widgets, properties has one key that matters:

  • markdown: the content, supports standard markdown

For metric widgets, properties can include:

  • title: chart title
  • metrics: the array of series to plot, see below
  • view: "timeSeries" for a line chart, "singleValue" for the KPI tiles at the top
  • region: which AWS region to query
  • period: seconds per datapoint
  • stacked: true stacks the series instead of overlaying them, used on Errors - HTTP Status Codes
  • stat: a widget level default statistic, redundant with the per-metric stat below but present on the Traffic - Request Rate widget
  • yAxis: left and right axis config, label, min, max, showUnits
  • annotations: horizontal and vertical reference lines, covered in Part 5
  • setPeriodToTimeRange: true makes a singleValue tile average over the whole selected time range instead of just the latest period, used on P95 Latency (ms)

Each entry inside metrics is its own array: Namespace, MetricName, then optionally DimensionName, DimensionValue pairs, then a trailing options object. That options object can carry stat, label, color, id, visible, and a per series yAxis of left or right, used in the Correlation View to plot four different scales on one chart. A metrics entry can also be a single math expression object instead of a namespace array, {"expression": ..., "label": ..., "id": ...}, covered in Part 5.

Basic Dashboard Structure:

JSON doesn't support comments, so notes on this block live here instead of inline. It's a simpler four-widget starting point to understand the shape of a dashboard body; Part 3 uses the fuller version below, not this one. If you want to try it directly, save it as basic-dashboard.json in your working directory, using a different name than dashboard.json so it doesn't collide with the Complete version below.

Four widgets, laid out with x/y/width/height in a 24-column grid: a text header at y0, then Request Rate and Error Rate side by side at y1, then Latency and Healthy Target Count side by side at y7. The Latency widget's annotations.horizontal block draws the red 500ms SLO line directly on the chart, that pattern repeats throughout the fuller dashboard below.

Complete Dashboard with All Sections:

This is the block Part 3 saves as dashboard.json, so it has to stay one intact, valid JSON file, which is why these notes sit outside it rather than as inline comments. Five sections, top to bottom by y coordinate:

  • y0: text header (markdown widget, not a metric)
  • y1: four singleValue tiles, current request rate, error rate computed with a metric math expression (m1/m2)*100, P95 latency, healthy target count
  • y4 to y16: the Golden Signals row, a text divider followed by four timeSeries widgets, traffic, stacked HTTP status codes, latency percentiles with SLO annotation lines, and target health
  • y17 to y22: EC2 Resource Utilization, CPU (with an 80 percent warning line), Memory and Disk from CWAgent, Network In/Out
  • y23 onward: Correlation View, one wide widget overlaying latency, request rate, 5XX errors, and CPU on the same timeline via yAxis: left/right, so you can visually line up a traffic spike with a latency spike

The Error Rate tile's {"id": "m1", "visible": false} pattern hides the raw inputs to a math expression while still showing the computed e1 result, the same trick used in Part 5's Math Expressions example.

Part 4: Test and Refine (10 min)

If you have no load balancer, the Request Rate, Error Rate, Latency, and Target Health widgets are expected to show "No data", this is not a bug to chase down. CPU, Memory, Network, and Disk should show real data within a few minutes.

View Dashboard:

  1. Go to CloudWatch → Dashboards
  2. Click "WebTierMonitoring"
  3. Verify all widgets load
  4. Check time range (default last 3 hours)

Test Correlation:

  1. Generate load on your application
  2. Observe how metrics correlate
  3. Note patterns (e.g., high load → high CPU → high latency)

Refine Layout:

  • Adjust widget sizes
  • Reorder for better flow
  • Add/remove metrics as needed
  • Test on mobile view

Part 5: Add Advanced Features (Optional) (5 min)

A dashboard is just the JSON you last pushed with put-dashboard, editing dashboard.json locally changes nothing on its own. You'll need to push it again after merging the examples below in, see the end of this section.

Add Annotations: annotations is a sibling of metrics, view, region, and period, all inside a widget's properties object, at the same nesting level. The horizontal SLO/warning lines already appear on the Latency and CPU widgets above; vertical, marking a single point in time, is the one technique not yet used anywhere in the Complete Dashboard. Add it to the CPU Utilization widget's existing annotations block to mark when a deployment went out, so you can see whether it lines up with a CPU or latency change. Add Math Expressions: this is the same id/expression pattern already used in the Error Rate tile at the top of the Complete Dashboard. m1 and m2 are hidden raw metrics (visible: false), and e1 is the computed result that actually gets plotted. To use it elsewhere, replace an existing widget's whole metrics array with this shape, it isn't added alongside the raw counts, it replaces them, since mixing raw counts and a computed percentage on one axis reads poorly. Reflection Questions

Answer these in your README:

  1. Why show P95 instead of average latency?

    • Hint: User experience vs system average

  2. What correlation patterns indicate problems?

    • Hint: High request rate + high CPU + high latency

  3. Why group related metrics?

    • Hint: Faster root cause analysis

  4. How many metrics is too many on one dashboard?

    • Hint: Balance completeness with comprehension

  5. When would you create multiple dashboards?

    • Hint: Different audiences, different purposes

Troubleshooting

Issue: Widgets showing "No data"

  • Verify metric namespace and name
  • Check dimensions (LoadBalancer ID, Instance ID)
  • Ensure metrics are being published
  • Check time range

Issue: Dashboard looks cluttered

  • Reduce to 6-10 key metrics
  • Group related metrics
  • Use larger widgets
  • Consider multiple dashboards
